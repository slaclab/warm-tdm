# Warm-TDM RSSI/SRP hardware report

## Result

- **Idle SrpRssi / DataRssi behavior:** Healthy. Over a 60 s counter baseline and a
  ~105 s packet capture, **both** cores stayed `rssiOpen=True` with
  down/drop/retran = 0 and no RST. Only the initial SYN handshake plus steady NULL
  keepalives (313/314 per core). **The historical ~52 resets/min does NOT reproduce**
  on the loaded image. (`02-idle-cap`, `01-idle`.) *Observed.*
- **Missing first response reproduced? Trials:** **Yes, once, intermittently.** In
  `14-columnB` the first SRP request after connect (id=1, `AxiVersion.FpgaVersion`,
  addr 0x0) reached the wire and was **transport-ACKed by the FPGA**, but the FPGA
  emitted **no SRP reply**; the op timed out at exactly `root_timeout`=1.0 s on an
  otherwise-healthy link (0 BUSY/drop/retran/reset). It did **not** recur: 7 cold
  A/B/C trials + 5 fresh `column-sequential` repeats (`17-coldseq-t1..5`) all issued a
  healthy first reply → **1 failure in 13 fresh first-reads**. *Observed (failure);
  frequency inferred from small N.*
- **Batched versus sequential behavior:** Sharp, reproducible split. Sequential reads
  are fast and clean; batched reads drive **host-side** RSSI BUSY (flags 0x41,
  host→FPGA) and, at full-column scale, a reset + transaction timeout:
  - `safb`: sequential ≈9–11 ms, `locBusyCnt` flat; batched ≈86–145 ms, `locBusyCnt`
    climbs, `dropCount` grows (order-independent — confirmed reversed in `11`).
  - `axi`: sequential ≈2.4 ms; batched ≈40–60 ms with BUSY growth.
  - **`column-batched` FAILED** (`13-columnA`): 176 host→FPGA BUSY, 112 retrans, 9
    drops, **1 SrpRssi reset+reconnect** ~260 ms into the burst → `Timeout waiting for
    register transaction 13` (LedEn); 33 tail SRP IDs orphaned by the reset.
  - `column-sequential` and `readall-sequential` (root) complete cleanly (1731/1731
    replies at root). *Observed.*
- **ScratchPad original restored and verified?** **Yes.** Original = `0x00000000`;
  wrote `0xA5A55A5A` and `0x5A5AA5A5` (both read back correct); restored to
  `0x00000000` and verified via `scratch_restored`. (`16-writectl`.) *Observed.*
- **Best-supported explanation; remaining uncertainty:** Two **distinct** phenomena.
  (1) **Batched-read host backpressure** — concurrent SRP bursts overrun the host RSSI
  receive path (`remBusy`=0 throughout → FPGA is not the bottleneck), escalating
  BUSY→drops/retrans→reset; large batches cross from "slow but completes" into
  "reset + timeout". Serializing eliminates it. (2) **Intermittent missing first SRP
  response** — a first post-connect request is transport-ACKed by the FPGA but never
  answered at the SRP application layer; localizes to **FPGA-side first-request
  processing**, not host backpressure or return-path loss. Uncertainty: the trigger
  for (2) is not isolated (1/13, all same fw/args); a host-only capture cannot prove
  FPGA internal state, only that no reply frame was emitted (FPGA RSSI seq never
  advanced).

## Representative failure and successful control

**Failure A — batched-read reset (`13-columnA`, column-batched, full ColumnBoard ReadAll):**
- First requested device: recursive `ColumnBoard[0]` ReadAll; failing leaf
  `WarmTdmConfig.LedEn` @0x7014, SRP id 13.
- Timeline (capture-relative; single host port 57096 = one epoch that reset in place):
  +0.000 s SYN handshake; +6.168→+8.317 s **176 BUSY pkts all host→FPGA (0x41)**;
  **+6.427 s RST** (host seq=19 ack=134 flags 0x11; FPGA echoes 0x10) ≈260 ms into the
  burst; **+6.527 s SYN reconnect**; +29.06 s RST = shutdown.
- First request captured/acked/answered/completed: request on wire; RSSI-level
  progress present, but 33 in-flight SRP IDs (381–413) never replied; API raised
  `Block::checkTransaction … Timeout waiting for register transaction 13`.
- ACK delays vs retransmits: 673 duplicate-payload FPGA→host frames (retransmissions)
  cluster with the BUSY window and precede/accompany the reset — consistent with a
  **late/backpressured host** (sustained host BUSY), not prompt-ACK-then-drop.
- Resets / duplicates / checksum / status: 1 mid-op reset; 673 dup payloads; all RSSI
  header checksums OK; no nonzero SRP status words observed.
- Matched control: `column-sequential` (`17-coldseq-t1..5`) and `readall-sequential`
  (`15-rootctl`, 1731/1731) complete cleanly — serialization removes the BUSY/reset.
- Observation vs inference: *Observed* host-only BUSY + reset + orphaned tail.
  *Inferred* host RSSI receive-queue backpressure as root cause (`remBusy`=0 ⇒ not FPGA).

**Failure B — intermittent missing first response (`14-columnB`, column-sequential):**
- First requested register: `AxiVersion.FpgaVersion` @0x0, SRP id 1.
- Timeline: server `SrpV3: Send frame for id=1` at capture **+6.307 s**; **pkt81
  host→FPGA seq=119 sof=1 id=1** on the wire at +6.307 s; **pkt82 (+6.312 s) FPGA→host
  ack=119** ⇒ FPGA RSSI **acknowledged** the request 5 ms later. FPGA then sends only
  bare ACKs (seq pinned at 129, ack walks 119→122 tracking host NULLs) — **no reply
  frame ever framed**. Timeout at **+7.308 s = exactly 1.0 s** (`root_timeout`).
- First request captured (**yes**) / acknowledged (**yes, transport**) / response
  captured (**no** — 0 replies with id=1 anywhere) / API completion (**timeout error**).
- ACK delays vs retransmits: none — 0 BUSY, 0 retrans, 0 drop, 0 reset; link healthy
  throughout (NULLs + ACKs normal).
- Resets/duplicates/status: none; no reset, no duplicate, connection stayed open (same
  port). Retry id=2 replied in 0.1 ms after the op aborted.
- Matched control: same session `row-stock` passed 3/3; 5 fresh `column-sequential`
  repeats all passed with id=1 replying in ~0.05 ms ⇒ intermittent.
- Observation vs inference: *Observed* request sent + transport-ACKed but no SRP reply
  emitted, timeout at root_timeout. *Inferred* FPGA-side first-request processing lapse
  (host-only capture cannot see FPGA internals; but FPGA seq never advanced ⇒ no reply
  was ever transmitted, ruling out return-path loss of an emitted reply).
